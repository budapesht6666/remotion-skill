## Remotion что за технология?

Remotion — это React-фреймворк для программного создания видео. Ты пишешь видео как обычные React-компоненты, а Remotion рендерит каждый кадр (через headless Chrome) и склеивает их в MP4 через FFmpeg.

Суть в двух вещах:

**Кадр как функция состояния.** Есть хук `useCurrentFrame()` — компонент получает номер текущего кадра и рендерит соответствующее состояние. Анимации делаются через `interpolate()` и `spring()`, то есть вся анимация детерминирована и вычисляется из номера кадра, а не через таймеры.

```tsx
const frame = useCurrentFrame();
const opacity = interpolate(frame, [0, 30], [0, 1]);
```

**Программный рендер.** Есть CLI и Node API (`@remotion/renderer`), поэтому видео можно генерить автоматически: подставил данные из JSON/API → отрендерил серверно → получил MP4. Есть Remotion Lambda для дешёвого параллельного рендера в AWS.

Для тебя это может быть особенно интересно в контексте генератора Shorts — Remotion как раз популярный движок для faceless-контента: субтитры с подсветкой слов по таймингам Whisper, анимированные графики, шаблоны с параметрами. Есть готовый пакет `@remotion/captions` и шаблоны типа TikTok-style captions. Стек TypeScript, что тебе подходит.

Из минусов: рендер небыстрый (браузерный рендер каждого кадра), и лицензия — бесплатно для физлиц и мелких компаний, но компаниям от 4 человек нужна платная Company License.

## Какого вида анимацию я смогу создавать? Я правильно понимаю допустим есть любая библиотека допустим которая работает с 3D и если она рендерит что-то то соответственно такое видео я и получу? Дай ссылки на YouTube посмотреть примеры рендеров

Да, ты правильно понимаешь принцип. Remotion делает скриншот каждого кадра из headless-браузера — значит **всё, что рендерится в браузере, попадёт в видео**. Единственное требование: анимация должна быть детерминированной, то есть привязанной к `useCurrentFrame()`, а не к реальному времени (setInterval, requestAnimationFrame сами по себе не сработают — кадр должен полностью зависеть от номера кадра).

Что реально можно делать:

- **3D через Three.js** — есть официальный пакет `@remotion/three` с компонентом `<ThreeCanvas>`, который синхронизирует react-three-fiber с таймлайном Remotion. WebGL-сцены, шейдеры, 3D-модели (GLTF) — всё рендерится в видео.
- **Canvas и WebGL напрямую** — любые генеративные штуки, партиклы, шейдер-арт.
- **SVG-анимации** — морфинг путей, анимация stroke-dashoffset, Lottie (есть `@remotion/lottie`).
- **Графики** — D3, Recharts, всё что угодно. Анимированные свечные графики для трейдинг-контента, например.
- **HTML/CSS** — типографика, kinetic text, субтитры, UI-анимации.
- **Видео и аудио как слои** — вставляешь `<OffthreadVideo>` фоном, поверх накладываешь свою графику. Визуализация аудио через `@remotion/media-utils` (спектрограммы под музыку).

Нюанс с 3D: тяжёлые WebGL-сцены рендерятся медленно, и на серверном рендере нужен GPU или software rendering (`--gl=angle` / swangle), иначе будут артефакты.

## Я правильно понимаю если я напишу такую программу и буду запускать её локально на своем ноутбуке Reisen 5800h хватит ли моих мощностей? Какие ограничения и чего лучше не делать?

Да, 5800H (8 ядер / 16 потоков) — вполне достаточно для локального рендера. Это как раз CPU-задача: Remotion параллелит рендер, открывая несколько вкладок headless Chrome, и каждая жуёт свои кадры. На 16 потоках это работает хорошо.

Реальные ориентиры для твоего кейса (Shorts, 1080×1920, 30fps, 30–60 сек):

- **2D-контент** (субтитры, текст, картинки, видео-фон) — рендер обычно быстрее длительности ролика или сопоставим: минута-три на ролик. Для автоматической генерации Shorts это норм.
- **RAM** — каждая вкладка Chrome ест 300–500+ МБ. Если у тебя 16 ГБ, ставь `concurrency` в районе 4–8, не оставляй дефолт «по числу потоков», иначе можешь упереться в память и словить своп.
- **Троттлинг** — это ноутбук, под длительной 100% нагрузкой 5800H греется и сбрасывает частоты. Рендер пачки роликов ночью — ок, но следи за охлаждением.

Чего лучше не делать / ограничения:

- **Тяжёлый WebGL/Three.js** — главное узкое место. У тебя скорее всего iGPU (Vega 8), headless Chrome на сервере часто вообще падает на software rendering (SwiftShader), и рендер 3D-сцены может идти в 10–50 раз медленнее реального времени. Простые 3D-сцены потянет, сложные шейдеры и партиклы — будет больно. Для Shorts 3D почти никогда и не нужно.
- **`<Video>` вместо `<OffthreadVideo>`** — если используешь видео-фоны, бери только `<OffthreadVideo>`, иначе получишь рассинхрон кадров и утечки памяти.
- **Загрузка ресурсов по сети внутри композиции** — шрифты, картинки, аудио держи локально или используй `delayRender()`/`continueRender()`, иначе будут пропущенные кадры и флаки.
- **4K и 60fps** — не надо. Для Shorts 1080p/30fps достаточно, а время рендера растёт линейно от числа кадров и квадратично-ощутимо от разрешения.
- **Очень длинные видео** — часовые ролики локально рендерить мучительно. Но твой формат — минута, так что это не про тебя.

Практический совет для пайплайна: рендери через Node API (`renderMedia()`), очередь роликов — последовательно, а не параллельно (пусть один рендер использует все ядра), и добавь `--gl=angle` если вдруг полезешь в WebGL. Если когда-нибудь упрёшься в масштаб (десятки роликов в день), тогда уже смотреть Remotion Lambda — но для старта ноутбука хватит с запасом.
